# 1. Build

## Build ทั้งหมด

ดับเบิลคลิก `build.bat` ที่โฟลเดอร์หลัก ผลลัพธ์จะอยู่ที่:

- `TrainerBuild\TBH Trainer.exe`
- `TrainerBuild\TBHHook.dll`

## สิ่งที่ต้องมี

- Windows x64
- .NET 10 SDK
- C++ compiler อย่างใดอย่างหนึ่ง: MinGW-w64 `g++` ใน `PATH` หรือ Visual Studio พร้อม x64 C++ build tools

Script จะเช็กให้ทั้ง 2 ขั้น ถ้าขาดเครื่องมือจะหยุดพร้อมบอกสาเหตุ

## Build แยกส่วน

```bat
cd TBHHook
build.bat

cd ..\TBH_Trainer
build.bat
```

## เรื่องที่ต้องรู้ตอน build

- **แก้ hook (`TBHHook`) ต้องปิดเกม** เพราะ DLL ยังถูกโหลดค้างอยู่ในเกมหลัง inject และต้องเปิดเกมใหม่ถึงจะใช้ตัวใหม่
- **แก้เฉพาะ trainer** ปิดแค่ trainer พอ
- ถ้าแก้ `SharedState` ต้อง build ทั้ง hook และ trainer พร้อมกัน
- ไฟล์ถูก build ไปที่ `publish\` แล้ว copy ต่อไปที่ `TrainerBuild\`

## โครงสร้างโปรเจกต์

```
TBH_Trainer\        C# WinForms trainer (.NET 10)
  *.cs              source ทั้งหมด
  app.manifest      ขอสิทธิ์ Administrator
  logo.png/icon.ico embedded resource
TBHHook\            C++ injected DLL
  dllmain.cpp       source
dump_1.2.x\         ผลจาก Il2CppDumper + CSV ของเกม (ไม่อยู่ใน git)
TrainerBuild\       ไฟล์ที่ใช้งานจริง (ไม่อยู่ใน git)
```

## วิธีใช้งาน

1. เปิดเกมให้เข้า run ก่อน
2. เปิด `TrainerBuild\TBH Trainer.exe` แบบ **Run as administrator**
3. กด **Connect** ปุ่มเดียว trainer จะทำต่อเองทั้งหมด: เลือก process → ACTk bypass → inject hook → scan hero → lock stat → เปิดตีทีเดียวตายและ God mode
4. Speedhack และ Item spawn กดใช้เพิ่มได้ตามต้องการ
5. กด Minimize แล้วหน้าต่างจะยุบไปที่ system tray มุมขวาล่าง คลิกซ้ายที่ไอคอนเพื่อเรียกกลับ
6. **ก่อนปิดเกมให้กด Disconnect ทุกครั้ง** (หรือปิด Trainer ก่อน) hook จะคืน speed ปกติแล้วหยุดเรียกเข้าเกม ถ้าปิดเกมตอนที่ hook ยังทำงานอยู่ เกมอาจ crash หรือค้างตอนปิด

## อัปเดตอัตโนมัติ (v1.4.1 ขึ้นไป)

ตอนเปิดโปรแกรม trainer จะเช็ก Release ล่าสุดของ repo `KEWI-hub/TBH-Trainer` (Public)

- **ทุกคนอัปเดตได้ ไม่ต้องมีบัญชี GitHub ไม่ต้องถูกเชิญ ไม่ต้องใส่ token** — repo เป็น public
  แล้ว เรียก GitHub API แบบไม่ล็อกอินได้เลย ถ้ามีเวอร์ชันใหม่จะขึ้นถามก่อน กดตกลงแล้วโหลด
  แตกไฟล์ทับ และเปิด trainer ใหม่ให้เอง
- เช็กเองได้ตลอดจากคลิกขวาไอคอนที่ tray → **Check for updates**
- เรียกแบบไม่ล็อกอินมีเพดาน 60 request/ชั่วโมง/IP ของ GitHub ซึ่งเหลือเฟือสำหรับเช็กตอนเปิดโปรแกรม
  ถ้าชนเพดานหรือเน็ตไม่ติด จะบอกเหตุผลใน log พร้อมลิงก์ให้โหลดเอง
- ต้อง**ปิดเกมก่อนอัปเดต** เพราะ `TBHHook.dll` ถูกล็อกอยู่ในเกม
- ออกเวอร์ชันใหม่: แก้ `AppInfo.Version` ใน `Updater.cs` ให้ตรงกับ tag (`v<เวอร์ชัน>`) แล้วแนบ zip ที่มี `TBH Trainer.exe` + `TBHHook.dll` ใน Release

ค่าที่ lock อัตโนมัติ: HP 2,000,000,000 / Attack Speed 50 / Crit Chance 1.0 / Crit Damage 100 / CDR 10 / Armor 5,000,000 (ตอนเปิด God mode)

ปุ่ม **Max stats (all heroes)** ตั้งทั้ง 8 ค่าให้ฮีโร่ทั้ง 3 ช่องพร้อมกัน: Attack Damage 1,000,000 / Attack Speed 50 / Crit Chance 1.0 / Crit Damage 100 / CDR 10 / Armor 5,000,000 / Move Speed 60 / Cast Speed 10

lock ทำงานอยู่ใน hook ที่อยู่ในเกม และผูกกับ**ช่อง** hero ไม่ใช่ตัวละคร จัดทัพใหม่ก็ยังอมตะ ตั้งแต่ v1.4.3 **กด Disconnect หรือปิด trainer แล้ว hook จะหยุดทุกอย่าง** (คืน speed ปกติ) จนกว่าจะ Connect ใหม่

## เปลี่ยนแปลงใน v3.1.1 (2026-10-30)

**แก้เกมกระตุกหลังกด Connect** (v3.1.0 ทำให้เกมเหลือ 2–3 fps เมื่อเล่นไปนานๆ)

- สาเหตุ: Auto open boxes เรียก `FindObjectsOfType` ทุก 250 ms และตัวอ่าน AbuseGuard (เพิ่มใน v3.1.0) เรียกทุก 1 วินาที
  คำสั่งนี้ไล่ค้น object ทั้งฉาก ในเซสชันที่เล่นมานานกินเวลาหลายร้อย ms ต่อครั้ง
  - วัดจากตัวนับเฟรมของ hook: Connect อยู่ 2–3 fps, สั่งพัก hook 60 fps, ปิดเฉพาะ Auto open boxes ~43 fps
- ตอนนี้เก็บผลค้นไว้หลัง GC handle แล้วค้นใหม่ทุก 10 วินาที (กล่อง) / 30 วินาที (guard) — ฟีเจอร์ไม่ได้ปิด กล่องยังเปิดทุก 2 วินาที
  - กล่องที่ถูกทำลายไปแล้ว (เปลี่ยนด่าน) ดูจาก `m_CachedPtr` (+0x10) จะถูกข้ามและสั่งค้นใหม่ทันที ไม่ให้เข้าใจผิดว่ากระเป๋าเต็ม
  - Unity 6: `il2cpp_gchandle_*` ใช้ handle ขนาด pointer (64 bit) ถ้าประกาศเป็น `uint32_t` เกม crash
- อ่าน AbuseGuard จาก static field ของ singleton `ob<T>` ก่อน ไม่ต้องค้นฉาก ไม่เรียก getter เพราะ getter (`gnl`) จะสร้าง GameObject ใหม่ถ้ายังไม่มี
  - guard มีอยู่จริงเมื่อเกมเรียก getter ครั้งแรกเท่านั้น จึงอาจขึ้น "not read yet" ช่วงต้นเซสชัน
- ค้นด้วย `FindObjectsByType(Type, FindObjectsSortMode.None)` แทน `FindObjectsOfType` (ไม่เรียงตาม instance ID)
  - วัด A/B ในเซสชันเดียวกัน วิธีละ 48 ครั้ง: 14.9 ms เฉลี่ย / 21.5 ms ช้าสุด → 8.3 ms / 11.1 ms
  - Self-check แสดงเวลาค้นของแต่ละวิธี
- ผลรวม: หลัง Connect เกมอยู่ 59–60 fps เปิดทุกฟีเจอร์

### Bag → stash ย้ายวัตถุโบราณ (relic) ด้วย (2026-10-28)

relic เป็นไอเทมชนิด GEAR ที่ไม่มีเลเวล (lv=0, key 7xxxxx เช่น 712008, 722006, 752002, 792001, 792002, 793020, 794006)
กฎ "เก็บเฉพาะ gear เลเวล 90+" จึงทิ้งมันไว้ในกระเป๋า ทั้งที่ลากเข้าคลังเองได้ปกติ
- `BagMoveStep`: gear ที่ level ≤ 0 นับเป็น relic ไม่โดนกฎเลเวล ย้ายเข้าช่องว่างของคลังธรรมดาเหมือนของอื่น
- Inventory scan แสดงเป็น `RELIC ... <- move to stash` และข้อความใน log/tooltip เปลี่ยนเป็น "gear 90+ and relics"

### ค่าสเตตัสแบบ dictionary เขียนจาก main thread เท่านั้น (2026-10-28)

อาการ: ที่ x5 มีฮีโร่ตายและภาพกระตุก (god mode เปิด, 32 locks) — Player.log มี `[System.Stage] StageCount Error` 72 ครั้งใน ~40 นาที
(ทุกครั้งมาจาก `StageManager.jcb(...)` → coroutine → `xi.kxf`) ส่วนรอบก่อนหน้าที่เล่น x1 ราว 8 นาทีมี 7 ครั้ง

สิ่งที่แก้ (ยังไม่รู้แน่ว่าเป็นต้นเหตุ แต่เป็นบั๊กจริง):
- 3.0.0 เขียนสเตตัส 19 ค่า (ต้านทานธาตุ 4 + StatType dictionary 15) ผ่าน `Dictionary.set_Item` ของเกม **จาก worker thread** ทุก ~66 ms
  ไปพร้อมกับที่ main thread อ่าน dictionary เดียวกัน และ set_Item เพิ่ม version ทุกครั้ง ทำให้ enumeration ที่เกมเปิดค้างอยู่พังได้
- ตอนนี้ `ApplyHeroLocks` เขียนค่ากลุ่มนี้เฉพาะบน main thread (`g_mainThreadId` จาก frame hook) และไม่เกิน 2 ครั้ง/วินาที/ฮีโร่
  ค่าที่เป็น field ธรรมดายังเขียนถี่เท่าเดิม
- frame hook มีรอบ ApplyHeroLocks ทุก 10 เฟรมแม้ god mode ปิด (เดิมมีเฉพาะตอน god mode เปิด) เพื่อให้ค่ากลุ่ม dictionary ยังถูกเขียน
- `set_Item` ของ dictionary ทั้งสองชนิดถูก cache ไว้ (`DictSetItem`) ไม่ต้องหาด้วยชื่อทุกครั้ง

**StageCount Error ไม่ได้มาจาก one-hit kill (วัดเมื่อ 2026-10-28):** ปิด one-hit kill แล้วก็ยังเกิด 32 ครั้งใน 18 นาที
และจำนวนเท่ากับบอสด่านที่ฆ่าได้แทบพอดี (32 ต่อ 31 บอส รอบก่อน 72 ต่อ 68 บอส)
call stack คือ `StageManager.jcb` (มอนตาย) → coroutine → `xo.xi.kxf(int)` ซึ่งคืน `TryStageEnterTryResult` คือขั้นตอนลองเข้าด่านถัดไปหลังจบด่าน
→ เป็นข้อความที่เกมเขียนเองทุกครั้งที่ผ่านด่านใน Plague ยิ่งเร็วยิ่งมาก ไม่ใช่สัญญาณว่า trainer ทำพัง
(ข้อสังเกตใน v2.4.1 ว่าเกมค้างตอนถึง 86 ครั้ง และปิด one-hit kill แล้วหาย วัดบนสภาพคนละแบบ — ตอนนั้นยังไม่มี Max stats ที่ใช้งานได้)

### Attack Damage / Damage Addition เขียนลง stat dictionary ด้วย (2026-10-28)

ทดลองปิด one-hit kill แล้วมอน Plague ตายยากมาก ทั้งที่ Max stats ใส่ Attack Damage 1,000,000 ไว้
→ field บน Unit (`+0x104` AttackDamage, `+0x25C` DamageAddition) เป็นแค่สำเนาที่ `Hero.hbf` คัดลอกมาจาก dictionary
ตอนคำนวณดาเมจเกมไม่ได้ใช้ค่าที่เราเขียนลง field
- เพิ่มแถว `Attack Damage (stat)` (StatType 1) และ `Damage Addition (stat)` (StatType 41) แบบ `kStatDict` ค่า 1,000,000 อยู่ใน Max stats
- เขียนบน main thread ไม่เกิน 2 ครั้ง/วินาที เหมือนค่า dictionary ตัวอื่น
- **ได้ผล (2026-10-28):** ปิด one-hit kill ที่ x5 มอนตายเร็วเหมือนเดิม ไม่มีมอนค้างหน้าฮีโร่ ฆ่าบอสด่านได้ 1.74 ตัว/นาที
  (เปิด one-hit kill ได้ ~2.1) กล่อง 0.39 ใบ/นาที ฮีโร่ไม่ตาย
- ข้อจำกัด: ตัวนับ "monsters killed" และตัวจัดการมอนค้างทำงานเฉพาะตอนเปิด one-hit kill
- เทียบในเกมเดียวกันที่ x5 (หลังแก้ dictionary ให้เขียนบน main thread):

  | | one-hit kill ปิด (17:50) | one-hit kill เปิด (35:00) |
  |---|---|---|
  | บอสด่าน/นาที | 1.74 | 2.06 |
  | กล่อง/นาที | 0.39 | 0.43 |
  | มอนค้างที่ต้องช่วย | 5 | 0 |
  | ฮีโร่ตาย / กระตุก | ไม่มี | ไม่มี |

  StageCount Error 114 ครั้ง ≈ บอสที่ฆ่า 113 ตัว ไม่มี exception ใน Player.log → **ใช้ค่าเริ่มต้น (เปิด one-hit kill) ต่อ**

ทำไมตอนใช้ 2.4.0 ไม่เห็นปัญหานี้: one-hit kill ของ 2.4.0 มี detour บน damage ของมอน (`HookedMonsterDamage`)
ที่เปลี่ยนดาเมจจากหมัดฮีโร่เป็น 1e9 — มอนตายจากหมัดฮีโร่เสมอโดยไม่สนสเตตัส 3.0.0 ถอด detour นี้ออก เหลือแค่กด HP มอนเป็น 1 จาก worker thread

### แก้แล้ว: ฮีโร่ตายทั้งที่ god mode เปิด (2026-10-28)

**สูตรดรอปของเกม** (แกะจาก 1.3.2: `0x933000`, `0xB666B0` กล่องธรรมดา, `0xB667A0` กล่องบอสด่าน)

- `SpeedBucket` x1–x5 (ปัดเศษ timeScale) เก็บเวลาที่อยู่ในด่าน, จำนวนมอนที่ตาย, กล่องแต่ละชนิด, จำนวนครั้งที่โดน guard บล็อก และเวลาที่ถูกบล็อก
  - เวลาที่ไม่มีมอนตายเกิน 60 วินาที (เมนู/โหลดฉาก) ไม่นับ
  - นับมอนได้เฉพาะตอนเปิด one-hit kill
- `ReadGuard` อ่านค่าตั้ง, จำนวน request ในหน้าต่างเวลา และเวลาบล็อกจาก instance (หาใหม่ทุกวินาทีด้วย `FindObjectsOfType`)

```

```

ตรงตามสมการที่ decompile ออกมาทั้งสองครั้ง และค่าอยู่คงที่ไม่ถูกเขียนกลับ

ของ Plaguelands** ซึ่งเป็นสามค่าที่ฮุกยังไม่ยอมเขียน เพราะเคยใส่ 10 ลงไปแล้วหีบหยุดดรอปทั้งหมด

ปุ่มจึงถูกลบ ไม่ใช่เพราะเขียนไม่ได้ แต่เพราะผลถูกโควต้ากลืนจนผู้เล่นไม่เห็นความต่าง

### Debug channel (เครื่องนี้เท่านั้น)

### Spawn item: เกมปฏิเสธ

(20 call sites อีกสามตัวศูนย์) เรียกแล้วมัน**อ่านไอเทมถูกต้อง** (คืน `quantityBefore` ตรงกับที่ถืออยู่จริง)

ลองครบแล้ว: `EItemGetSourceType` ทั้ง 8 ค่า, bool ทั้งสองค่า, ลำดับอาร์กิวเมนต์ 5 แบบ — ไม่มีอันไหนเพิ่มของได้

### แก้แล้ว: ฮีโร่ตายตอนเร่งความเร็ว

ปัญหานี้ค้างมาตั้งแต่ 1.3.0 และปิดได้แล้วด้วย `do speedwatch` ที่ Plaguelands 23-20

**สาเหตุ** — ตอนเปลี่ยนด่าน เกม**รีเซ็ตฮีโร่ทั้งสามตัวกลับเป็น HP พื้นฐานพร้อมกัน** ข้างใน update ของตัวเอง
แล้วเดินการจำลองต่อในเฟรมเดียวกัน ตัววัดจับได้ตรงๆ:

```
t+45.2s frame 2175: max HP is NOT ours - hero ...540 hp=4392 max=4392
t+45.2s frame 2175: max HP is NOT ours - hero ...000 hp=1260 max=1260
t+45.2s frame 2175: max HP is NOT ours - hero ...A80 hp=1270 max=1270
```

ทั้งสามตัว เฟรมเดียวกัน `hp == max` และ pointer เดิม — คือการรีเซ็ต ไม่ใช่เกิดใหม่

ช่องโหว่กว้างหนึ่งเฟรมเท่ากันทุกความเร็ว แต่ที่ 20x หนึ่งเฟรมกินเวลาจริง 313–2,094 ms ซึ่งเท่ากับ
**เวลาในเกม 6–40 วินาที** ที่ 5x เฟรมเดียวกันคิดเป็นเศษเสี้ยวเท่านั้น การไล่เขียน 2e9 ทุกเฟรมจึงช่วยไม่ได้
เพราะดาเมจลงไปแล้ว*ระหว่าง*สองเฟรม

**วิธีแก้ — เลิกไล่เขียน ไปดักดาเมจแทน**

| | ทำอะไร |
|---|---|
| God mode | detour `pp.hby(float, Unit)` แล้ว**ไม่เรียกของเดิม** ฮีโร่ไม่รับดาเมจเลย |
| One-hit kill | detour `pl.hby` เปลี่ยนดาเมจเป็น 1e9 **เฉพาะตอนผู้โจมตีเป็นฮีโร่** แล้วเรียกของเดิมต่อ |

มอนใช้ `pl` ฮีโร่ใช้ `pp` คนละ address กัน สองตัวนี้เลยไม่ชนกัน

**One-hit kill ต้องเรียกของเดิมต่อเสมอ** เพราะของดรอปเฉพาะตอนฮีโร่ฆ่าเอง การขยายดาเมจทำให้ยังวิ่งผ่าน
ทางฆ่าของเกม — วัดจริงได้ 1 หีบจาก 618 ครั้ง ตรงกับอัตรา ~0.06%/ตัวที่เคยวัดไว้ **ห้ามกลับไปฆ่ามอนตรงๆ**

ทั้งคู่ตรวจ prologue ก่อนแพตช์ และสลับแค่ 8 ไบต์แรกแบบ aligned ครั้งเดียวด้วย `InterlockedExchange64`
เธรดหลักจึงไม่มีทางวิ่งเข้า jump ที่เขียนค้างครึ่งตัว

**ผลหลังแก้: 90 วินาทีที่ 20x — 4,348 เฟรม บล็อกดาเมจ 33,098 ครั้ง ตาย 0** เพดาน 5x ไม่ใช่สิ่งที่กันฮีโร่ตาย
อีกต่อไปแล้ว แม้จะยังเป็นค่าเริ่มต้นอยู่

### API ตรวจปัญหาตอนเร่งความเร็ว

`do speedwatch <วินาที> [ความเร็ว]` เก็บตัวอย่างทุกเฟรมแล้วสรุปว่า: เฟรมเรต, เฟรมที่แย่ที่สุด, จำนวนฮีโร่,
HP ต่ำสุด, จำนวนที่ตาย, เฟรมที่มีฮีโร่ HP 0 และ **เฟรมที่ max HP ไม่ใช่ 2e9** (คือเฟรมที่ god mode ไม่ลง)

ถ้าให้ความเร็วมาด้วย มันจะเร่งเองในช่วงที่วัด **ทะลุเพดาน 5x ได้** แล้วคืนค่าเดิมเมื่อจบ เพราะเครื่องมือที่ไปถึง
20x ไม่ได้ ก็ตอบคำถามเรื่อง 20x ไม่ได้

ผลรอบแรกที่ด่าน 3-10: **20x นาน 25 วินาที 1,318 เฟรม ไม่มีใครตาย god mode ลงครบทุกเฟรม** แปลว่าอาการ
ที่เจอตอน 1.3.0 ไม่ได้เกิดจากความเร็วอย่างเดียว ต้องรันตัวนี้ตอนอยู่ Plaguelands 23-20 ถึงจะจับตัวการได้

### Max HP ย้ายที่ — God mode เคยเขียนผิดช่อง

health controller ของ 1.3.0 **แทรก float เพิ่มมา 1 ตัว** (1.2.8 มี 6 ตัวที่ 0x38–0x4C แล้วต่อด้วย
object ที่ 0x50 ส่วน 1.3.0 มี 7 ตัวที่ 0x38–0x50) ทุกอย่างหลังจุดที่แทรกเลื่อนไป 4 byte

Max HP จึงย้ายจาก `+0x4C` ไป `+0x50` ยืนยันจากเกมจริง: ฮีโร่ HP เต็ม 1270 อ่าน `+4C=0` และ
`+50=1270` **ถ้าไม่แก้ God mode จะเขียน 2,000,000,000 ลง field ที่ไม่รู้ว่าคืออะไร** และไม่ได้
ตั้ง Max HP จริง

ตอนนี้ offset มาจาก build profile แทนที่จะ hard-code ไว้ใน hook (1.2.8 = `0x4C`, 1.3.0 = `0x50`)
และ Hero diagnostics พิมพ์ `+50` กับ `+54` พร้อมบอกว่าอ่าน Max HP จาก offset ไหน — เกมอัปเดต
ครั้งหน้าจะอ่านจาก log ได้เลยไม่ต้องเดา

`SharedState` เป็น **124 byte** — ต้องใช้ exe กับ hook เวอร์ชันเดียวกัน

### สิ่งที่ค้นพบ: มีแต่ฮีโร่ฆ่าเท่านั้นที่ของดร็อบ

ทดสอบวัดผลจริง 4 รอบ รอบละ 10 นาทีที่ด่าน 23-20 (Chest log + ตัวนับการตายแยกตามวิธี):

| วิธีที่ hook ใช้จัดการมอนค้าง | ฮีโร่ได้ฆ่า | กล่องจากมอนธรรมดา |
|---|---|---|
| `Monster.gwm()` เรียกตรง | 8.5% | 2 |
| ยิง damage ผ่าน `pl.gxf()` | 12.4% | 5 |
| ยกมอนไปวางข้างฮีโร่ | 14.0% | 2 |
| **ไม่แตะเลย ปล่อยฮีโร่ฆ่า** | **100%** | — |

ทุกรอบจำนวนกล่องเท่ากับที่ทำนายได้จาก **จำนวน hero kill เพียงอย่างเดียว** (~0.06% ต่อตัว)
ส่วนมอนที่ hook ฆ่าเองให้ของ **0 ใบ** ไม่ว่าจะเรียกผ่านเส้นทางไหน

**สรุป: การฆ่าที่ hook เป็นคนสั่ง ไม่ทอยของ** ต่อให้เรียกเมธอดเดียวกับที่ฮีโร่เรียกก็ตาม

### ตัวจัดการมอนค้างกลายเป็นตาข่ายนิรภัยอีกครั้ง

v2.0.4 ตั้งเวลารอไว้ 100 ms ซึ่งทำให้ hook ฆ่ามอน **เกือบทุกตัว** (วัดได้ 58,443 ตัวในเซสชันเดียว)
เท่ากับแย่งของดร็อบจากฮีโร่ไปเกือบหมดโดยไม่มีใครรู้

ตอนนี้รอ **1 วินาที** แล้วค่อยเริ่ม และลำดับการจัดการเปลี่ยนเป็น:

```
1.0 วิ   → ยกมอนไปวางที่ฮีโร่ (ฮีโร่ฆ่าเอง = ได้ของ)
+0.25 วิ → ยกอีก สูงสุด 3 ครั้ง
+0.25 วิ → ยิง damage
+0.25 วิ → ฆ่าปิดท้าย (ไม่ได้ของ แต่ไม่ค้าง)
```

และ **Skill Range ใน Max stats ขึ้นเป็น 20** ซึ่งเป็นตัวที่แก้อาการค้างได้จริง — ที่สปีดต่ำกว่า ~5x
แทบไม่มีมอนค้างให้ hook ต้องแตะเลย ของจึงดร็อบครบ

ตัวนับใน Self-check บอกตรงๆ ว่าใครฆ่า: `monsters killed: N by a hero, M by our damage, K by the death call`
นับตอนมอนหายไปจาก unit list จริง ไม่ใช่ตอน "เรียกแล้วไม่ error"

### กินแรมน้อยลง 93%

Trainer ที่เปิดทิ้งไว้เคยกิน working set ~109 MB ตอนนี้ **~8 MB** — คืนหน่วยความจำให้ Windows
เมื่อย่อลง tray และอัตโนมัติอีกครั้งหลังเปิดโปรแกรม 60 วินาที (CPU ตอน idle เป็น 0% อยู่แล้ว
ทั้งก่อนและหลัง ไม่มีอะไรให้ลด)

- log ไม่โตไม่สิ้นสุดอีกต่อไป ตัดครึ่งเก่าทิ้งเมื่อเกิน 24,000 ตัวอักษร
- ปิด concurrent GC และ EventSource ที่ไม่ได้ใช้

### build.bat เลิกโกหก

`TBH_Trainer\build.bat` เคยขึ้น `BUILD OK` ทั้งที่ copy ไป `TrainerBuild` ล้มเหลว (เพราะ trainer
หรือเกมล็อกไฟล์อยู่) ทำให้เอาไฟล์เก่าไปทดสอบโดยไม่รู้ตัว ตอนนี้เช็ค errorlevel ทุกจุด

และพบว่า .NET SDK **เลิก copy `TBHHook.dll` ลง `publish` แล้ว** ซึ่งถ้า package จากโฟลเดอร์นั้น
zip จะไม่มี hook เลย — ตอนนี้ build.bat ดึง hook จาก `TBHHook\TBHHook.dll` ตรงๆ ทั้งสองปลายทาง

### บั๊กที่จับได้ก่อนปล่อย

v2.0.5 (ไม่เคยขึ้น release) เปิด `InvariantGlobalization` เพื่อประหยัดแรม ผลคือ **สลับคีย์บอร์ด
เป็นภาษาไทยแล้ว Trainer ตายทันที** — WinForms สร้าง `CultureInfo(1054)` ตอนได้รับ
`WM_INPUTLANGCHANGE` ซึ่งทำไม่ได้ใน invariant mode ถอดออกแล้ว พร้อม comment กำกับว่าห้ามใส่กลับ

อีกตัว: `TrimMemory()` เคยเรียก `GC.WaitForPendingFinalizers()` บน UI thread ทำให้ Windows
ปิดโปรแกรมเพราะ AppHang ย้ายไป thread pool แล้ว

### สิ่งที่รู้เพิ่มเกี่ยวกับกล่องโรคระบาด

- กล่องมี**เพดานการถือครอง** ถ้าถือครบแล้วไม่เปิด **กล่องใหม่จะไม่ดร็อบเลย** (ไม่ใช่ดร็อบน้อยลง)

- ค่าที่เก็บใน `MaxAmountPlagueNormalChest` อ่านได้ 5 ขณะที่เพดานจริงคือ 20 และค่านี้ไม่ขยับ
  ตอนเก็บกล่อง จึง**ไม่ใช่จำนวนกล่อง** — น่าจะเป็นเลเวลอัปเกรด ยังไม่ได้พิสูจน์
- เขียนค่าพวกนี้แล้ว**ไม่ติดข้ามการปิดเปิดเกม** โหลดใหม่จากเซฟทุกครั้ง
- เกมไม่ clamp ค่าเหล่านี้เลย (เขียน 1,000,000,000 ก็รับ) จึงไม่มี "เพดานที่เกมออกแบบไว้"
  ให้ดันไปหา ตัวโอกาสดรอปกล่องจึงเป็น **อ่านอย่างเดียว**
- ชนิดกล่องคือ `EBoxType` (NORMAL 0 / BOSS 1 / ACTBOSS 2) × `EContentType` (NONE 0 / PLAGUE 1)
- ตอนจบด่านเกมยิง request ไป backend (`StageClearFunction`) แล้วรอคำตอบ เป็นเวลาจริงที่
  เร่งสปีดไม่ช่วย จึงเป็นพื้นตายตัวของรอบการเล่น

# 4. สิ่งที่แก้ใน hook ให้ทนการอัปเดตเกม

- **1.2.4 ไม่ export `il2cpp_method_get_pointer`** จึงใช้ `MethodPointer()` อ่านจาก `MethodInfo->methodPointer` (field แรก) แทน ถ้าไม่มีส่วนนี้ การหา method จาก RVA จะล้มเหลวเงียบๆ ทั้งหมด
- **หา item API จาก RVA ไม่ใช้ชื่อ** เพราะ 1.2.4 เอาชื่อสั้นเดิมไปใช้กับ class อื่น (`ti` กลายเป็น class save data) และมี method หลอกที่ signature ซ้ำกัน
- **หา singleton จาก type**: `FindSingletonInstance()` รับ static field ที่ทั้ง type และ class ของค่าเป็น class นั้นเอง ชื่อ field อย่าง `bbwm` เปลี่ยนก็ไม่พัง
- **หา database item จากชื่อ field** (`itemInfoData` + `currencyInfoData`) ที่ obfuscator ไม่แตะ (`yq` บน 1.00.09 = `bco` บน 1.2.4)
- **ตัด fallback ไป 1.00.08 ทิ้ง** พอ trainer ส่ง profile แล้ว RVA ที่ไม่มีจะเป็น 0 แทนที่จะไปเรียก address เก่าซึ่งทำให้เกม crash
- Hero lock เก็บตามช่อง แล้วใส่ค่าซ้ำทุก ~0.2 วินาที (~33 ms ตอน God mode) รวมถึง hero ที่ spawn หรือฟื้นทีหลัง
- `SharedState` ขยายเป็น 84 byte (`rvaItemInfo` ที่ 0x50)

# 7. วิธี migrate เมื่อเกมอัปเดตครั้งหน้า

ทุกครั้งที่เกมอัปเดต `GameAssembly.dll` จะถูก compile ใหม่ RVA และชื่อที่ obfuscate ไว้จะเปลี่ยนหมด
Trainer จะปฏิเสธการ patch เมื่อ byte ไม่ตรง (ปลอดภัย) และขึ้น pop-up บอกว่าไม่รองรับ

## ขั้นที่ 1 — ตรวจเวอร์ชัน

อ่าน `Version.txt` ในโฟลเดอร์เกม และ `buildid` ใน `steamapps/appmanifest_3678970.acf`

**ระยะ RVA → file offset เปลี่ยนทุก build** ต้องหาใหม่เสมอ ห้ามเอาของ build ก่อนมาใช้

| build | delta |
|---|---|
| ≤ 1.3.0 | `0xE00` |
| 1.3.1 | `0x1200` |
| 1.3.2 | `0x1A00` |

**และ `Version.txt` ไม่พอ** — 27 ต.ค. 2026 Steam เขียน `GameAssembly.dll` กับ `global-metadata.dat`
ใหม่ทั้งคู่โดยที่ `Version.txt` ยังเป็น `1.3.2` เหมือนเดิม วิธีที่เชื่อได้คืออ่านไบต์ที่ file offset ของ
ACTk ทั้ง 6 ตัวแล้วเทียบกับ prologue ใน profile ถ้าตรงครบแปลว่าเป็นการ revalidate ไม่ใช่ patch

## ขั้นที่ 2 — หา ACTk RVA ชุดใหม่

Detector ทั้ง 6 ตัวมักเรียงตัวเหมือนเดิมและเลื่อนไปพร้อมกันทั้งชุด ใช้วิธี scan หา prologue 6 byte ของทั้ง 6 ตัวที่ระยะห่างสัมพัทธ์เท่าเดิม แล้วยืนยันว่าเจอตำแหน่งเดียว จากนั้นกรอกลง `GameBuildProfile` เป็น profile ใหม่

prologue ที่ใช้:

| Detector | Signature |
|---|---|
| ObscuredCheatingDetector.Check | `41 56 48 83 EC 20` |
| ObscuredCheatingDetector.Compare / CompareExt | `48 89 5C 24 10 48` |
| InjectionDetector.Check | `40 53 48 83 EC 20` |
| SpeedHackDetector.Update | `40 56 48 83 EC 70` |
| SpeedHackDetector.OnApplicationPause | `48 89 5C 24 08 57` |

อย่าลืมคำนวณ disk offset ใหม่จาก section header (`RVA − (VirtualAddress − PointerToRawData)` ของ section `il2cpp`)

## ขั้นที่ 3 — ยืนยัน layout ของ hero

ต่อเกมแล้วกด **Dump hero layout** ในแท็บ Hero Stats จะได้ field/offset/RVA ของ `StageManager`, `Hero`, `Unit`, health controller และ `ObscuredFloat` โดยอ่านแค่ metadata ไม่แตะ memory ของ object จึงปลอดภัยทุกเวอร์ชัน ไฟล์จะถูกบันทึกไว้ข้างๆ trainer

## ขั้นที่ 4 — หา item API ใหม่

รัน Il2CppDumper กับ `GameAssembly.dll` + `TaskBarHero_Data/il2cpp_data/Metadata/global-metadata.dat` แล้วหาใน `dump.cs`:

- method ที่คืนค่า `AddItemResult` (ตัวเพิ่ม item) → ใส่ `ItemAddRva`
- method static ที่รับ `int` แล้วคืน `ItemInfoData` (ตัวหา item) → ใส่ `ItemInfoRva`

ระวัง: obfuscator ใส่ method หลอกที่ signature ซ้ำกันไว้เยอะ ให้เลือกตัวที่ไม่ซ้ำ และตรวจว่า RVA นั้นไม่ถูกใช้ซ้ำกับ method อื่น
ถ้าเจอหลายตัวที่ signature เหมือนกัน (แบบ 1.2.6) ให้เทียบขนาด function จาก `.pdata` และ call target ข้างใน ถ้าเรียก function ชุดเดียวกันคือโคลนที่ใช้แทนกันได้

## ขั้นที่ 5 — ดึง CSV ของเกม (ถ้าต้องการข้อมูล item)

ตาราง data เก็บเป็น CSV แบบอ่านได้ใน `TaskBarHero_Data/sharedassets0.assets` มองหา BOM (`EF BB BF`) แล้วอ่าน TextAsset ออกมา

## ขั้นที่ 6 — ทดสอบ

| จุดที่ต้องเช็ก | ผลที่ควรได้ |
|---|---|
| Connect | log ขึ้น `Detected game build: <เวอร์ชัน>` |
| ACTk | 6/6 OK |
| Speedhack | ความเร็วเกมเปลี่ยน |
| Hero lock | HP / Attack Speed เปลี่ยนจริงในเกม |
| ตีทีเดียวตาย | มอนตายในทีเดียว ดรอปของปกติ |
| Item spawn | ของเข้า inventory |

# 8. การหา pointer ด้วย Cheat Engine (วิธีสำรอง)

ใช้เมื่อ dump ไม่ได้ หรืออยากยืนยันค่าที่เจอ

1. เข้าเกมให้อยู่ในการต่อสู้ที่มี hero
2. Cheat Engine → Attach `TaskBarHero.exe`
3. **Mono → Activate mono features → Dissect mono**
4. ใน `Assembly-CSharp.dll` หา `TaskbarHero.StageManager` (ดู static field ที่เป็น singleton) หรือหา instance ของ `TaskbarHero.Hero` / `TaskbarHero.Unit`
5. ที่ hero: field `UnitHealthController` → ในนั้นหา float ที่เปลี่ยนตอนโดนตี = HP
6. คลิกขวาที่ float นั้น → **Pointer scan** แล้วกรองเฉพาะ chain ที่ base เป็น `GameAssembly.dll` และนิ่ง

**ข้อควรรู้:** ชื่อ class ใน Mono dissector (เช่น `ue.Stash`, `26432251c10 : ue.ti`) ใช้ยืนยันชื่อได้อย่างเดียว ตัวเลขนำหน้าเป็น pointer ของ metadata ไม่ใช่ offset ที่ใช้ใน trainer
ส่วน stat ของ hero เป็น `ObscuredFloat` ของ ACTk จะเห็นเป็นค่าที่เข้ารหัสไว้ ต้องถอดด้วย `hiddenValue XOR cryptoKey` (layout: hash +0x00, hiddenValue +0x04, cryptoKey +0x08, fakeValue +0x0C)

# 9. หลักความปลอดภัยของ trainer

- ทุกการเขียน memory และการเขียนไฟล์ผ่านการเช็ก byte signature ก่อน เวอร์ชันไม่ตรงจะปฏิเสธ ไม่เขียนทับมั่ว
- ACTk patch ถูกคืนค่าเดิมตอนกด Disable และตอนปิดโปรแกรม
- Feature ที่ยังไม่ verify กับเวอร์ชันนั้นจะถูกปิดทั้งฝั่ง trainer และฝั่ง hook เพื่อไม่ให้เรียก native code ที่ address ผิด
